## 1. 数据准备与动手前踩到的坑

这周我分到的数据集是 `Marathon`（ACL 2024，一共 1,530 道长上下文选择题，分成 6 类任务）。把官方仓库 `Hambaobao/Marathon` 克隆下来打开 `marathon.json` 后，先遇到两个实际问题：

1. **官方压缩包里没有标准答案**：`marathon.json` 全是题目和 A/B/C/D 选项，一条 `answer` 都没有（0/1,530）。按官方 README 的说法是要把预测 JSON 传到 `https://openbenchmark.online/marathon/` 在线算分，但现在那个网站访问直接报 `HTTP 521` 挂了，没法在线评测。
2. **从上游源数据集还原真值和 `evidence`**：查了一下论文来源，Marathon 的题主要改写自 `bigai-nlco/LooGLE` 和 `THUDM/LongBench`。于是我写了个匹配脚本（`src/build_marathon_eval_set.py`），把 `LooGLE`（`longdep_qa.jsonl`、`shortdep_qa.jsonl`）和 `LongBench`（`passage_retrieval_en.jsonl`）全拉下来对齐。
   - 这里还躲过一个坑：`passage_retrieval` 类题目在 Marathon 里把段落顺序重新打乱并重编号了（比如 LongBench 原题答案是 `Paragraph 28`，Marathon 的四个选项里只有 `Paragraph 1/2/7/8`）。如果直接照搬上游编号肯定全错，后来改成提取上游目标段落的正文片段，再回 Marathon 原文里反查对应段落号，才稳稳匹配回来。
   - 最终一共还原出 1,182 条带标准答案和 `evidence` 原句的样本（`comprehension_and_reasoning` 314、`multiple_information_retrieval` 311、`timeline_reorder` 145、`computation` 97、`shortdep_qa` 282、`passage_retrieval` 33）。

为了控制 API 预算同时保证各组实验可对比，我用固定种子 `seed=42` 从 6 类任务里各抽 20 题，固定了一个 **120 题的主评测集**（`data/eval_split_main.jsonl`）。后面所有实验全跑在这同一批 120 题上。

## 2. Thingo 接口试跑情况

按群里通知统一用 `gpt-6-sol`（后面补完 `GPT特惠` Key 跑的）；在这之前我也先拿 `gemini-3.8-flash` 跑了第一轮，期间测出两个挺关键的接口现象：

- **每条请求固定多算 ~5K 输入 token**：哪怕只发一句 `"Reply with exactly OK."` 且完全不传 `tools`，`gemini-3.8-flash` 返回的 `prompt_tokens` 也有 `4,917`，`gpt-6-sol` 也有 `5,588`。说明中转网关后台给每次请求都拼了一段大约 5K tokens 的系统前缀。这直接决定了后续“切块多轮调用”会按调用次数放大基础前缀开销。
- **速度与稳定性差异**：`gemini-3.8-flash` 白天能跑但非常慢（单题平均 77.6s），而且凌晨 0 点后连续读超时；切到 `gpt-6-sol` 后单题稳定在 4～5 秒左右，120 题两分钟就能跑完。

## 4. 错题复盘：到底为什么跑不满？

把错题和 `LooGLE` 的原始 `evidence` 对着看之后，发现基线跑不满的原因其实分成了**网关/运行环境层**和**长文本任务自身**两大块，一共梳理出 8 类具体问题：

### 4.1 跑 `gemini-3.8-flash` 时暴露的 3 类工程问题

1. **并发长文本偶发 502（G1 错 9/15，占 60.0%）**：8 并发跑十万字上下文时，中转直接报错 `HTTP 502: bad_response_status_code`（如 `id=219, 238, 85, 41, 1212`）。
2. **没传 tools 却触发 `finish_reason="tool_calls"` 返回空串（G1 错 4/15，G2 暴增到 34/41 占 82.9%）**：这个现象一开始很反直觉——请求体里根本没传工具列表，结果模型返回 `content=""` 且结束原因是 `tool_calls`。尤其在 36K 截断把关键段落删掉后，模型在原文找不到线索，就试图去调网关注入的隐藏工具来搜原文，结果请求直接空返回。
3. **推理 token 吃光输出额度（G1 错 2/15，G2 错 4/41）**：比如 `id=575`（在 14.5 万字符里数 `POCKETWATCH` 出现次数）和 `id=805`（15.1 万字时间线重排），哪怕把 `max_tokens` 设到 `3072` 还是在思考过程中用完了额度，JSON 没来得及输出就被截断（`finish_reason="length"`）。

### 4.2 跑 `gpt-6-sol` 时暴露的 5 类语义与数据问题

`gpt-6-sol` 没再出现接口报错和空串，S1 全量错了 3 题，S2 截断错了 14 题，正好把题目本身的难点露出来了：

1. **先验记忆压过原文细节（跨段计算失误，S1 占 2/3，S2 占 4/14）**：
   最典型的是 `id=925`（222,894 字符）：问猫王在拉斯维加斯 International Hotel 演了几年。原文脚本里明确有一句 `"WELCOME BACK FOR YOUR FIFTH YEAR"`（正解 `C: 5 years`）。结果全量直喂时 `gpt-6-sol` 漏掉了这一行，直接用自己背过的现实历史常识（猫王 1969–1976 年驻场 7 年）选了 `A: 7 years`。另一道 `id=923`（134,790 字符）是因为两个时间锚点隔得太远且一个是 `"1679"`、一个是模糊的 `"late 17th century"`，把 20 年算成了 25 年。
2. **多跳线索分散与双问句陷阱（S1 占 1/3，S2 占 4/14）**：
   36K 截断把中段线索删掉后，`id=278, 215, 166, 530` 都会靠残片猜错。另外 S1 全量唯一错的一道非计算题 `id=135` 挺值得注意：问题连着问了两句（“医生为什么不想去失踪的船？这是否预示着可怕的结局？”），`gpt-6-sol` 选的 B 精准对应前一句的医疗顾虑，而原数据集给的标准答案 D 只回答了后半句且句式明显比其他选项生硬，属于数据集构造本身带偏。
3. **跨段信息遗漏导致时序重排错误（S2 占 2/14）**：
   比如 `id=805, 812`，事件分散在不同章节，截断掉中间段之后，模型只能按剩下的片段猜顺序。
4. **段落摘要匹配不上（S2 占 3/14）**：
   `id=1168, 1212, 1244`，对应段落被截断后 `passage_retrieval` 只能盲选。
5. **局部相似词干扰（S2 占 1/14）**：
   选项里编造了包含原文高频词的似是而非句，局部上下文不全时很容易踩坑。

另外，我用 `LooGLE` 给的 `evidence` 算了一下原文出现位置对准确率的影响，能明显看到**中段（33%–67%）最容易出错**（也就是常说的 Lost in the Middle）：

- `gemini-3.8-flash` 全量：开头 `88.57%`（31/35）→ **中段 `81.82%`（36/44）** → 结尾 `94.74%`（18/19）
- `gpt-6-sol` 36K 截断：开头 `85.71%`（30/35）→ **中段 `81.82%`（36/44）** → 结尾 `94.74%`（18/19）；而且长度 `>=150K` 的超长题准确率会从 `60K–100K` 的 `92.86%` 一路掉到 `76.47%`（13/17）。

## 5. 改进做法与对比（收益、代价、边界）

针对上面“窗口受限时中段证据丢失”和“20 多万字直喂容易漏掉针尖细节（像 `id=925`）”的问题，我在 `src/run_improved.py` 里按 `rsi-flow` 的分支+并行思路搭了一个三步小流程：

- **长度分流**：不超过 36K 字符的短文本直接做；超过 36K 的按换行/句号切分成带 1,200 字符重叠的 `<=32K` 小块（保证每一步请求都严格不超 36K 窗口）；
- **并行取证（Map）**：并发让模型在每个块里只做一件事——把跟问题/时间/次数/段落有关的原话摘出来（同时显式声明没有外部工具，防止触发 `tool_calls`）；
- **汇总判断（Reduce）**：把各块抽出的证据按原文顺序拼好，再做最后的选择题判断；如果 JSON 格式不对再走一次兜底修复。

跑完同一批 120 题（详细统计在 `results/comparison_6sol.json`）：

1. **收益（对比同等 36K 单步窗口的 S2 基线）**：
   - 准确率从 **88.33%（106/120）提升到 96.67%（116/120）**，净多对 10 题（修好了 12 题，退化 2 题）；
   - 五类被截断拖垮的任务全部大幅回升：`comprehension_and_reasoning` 80%→95%、`passage_retrieval` 85%→100%、`multiple_information_retrieval` 90%→100%、`computation` 85%→90%、`timeline_reorder` 90%→95%；
   - 相比不截断直接喂 25 万字符的 S1 全量基线（97.50%），几乎追平，还顺带救回了 S1 都做错的那道 22 万字猫王计算题 `id=925`（Map 阶段把 `"WELCOME BACK FOR YOUR FIFTH YEAR"` 单独摘了出来，没被先验记忆带偏）。

2. **代价（多出来的花销和耗时）**：
   - **Token 和费用明显变高**：Prompt Tokens 从 S1 的 361 万涨到 634 万（**1.75 倍**），成本从 ¥1.25 涨到 ¥2.31（**1.84 倍**，是 S2 截断基线的 **4.04 倍**）。除了 1,200 字符重叠和每块重复带题目外，很大一块是被前面测到的“网关每次调用固定 5.58K 前缀”放大了。
   - **耗时变长**：单题累计请求时间从 5.02 秒涨到 28.86 秒。

3. **边界（改进版反而做错的 2 道退化题）**：
   - **`id=861`（过度弃权）**：计算两个人被处决的间隔天数，两个日期分散在不同分块里，前面抽漏了一个日期，汇总时因为提示词要求严格核对，模型直接输出了 `{"option":null}` 放弃作答，反而丢分。
   - **`id=805`（闪回式叙事时序跨块混淆）**：原文是个剧本，第 3 块写了老年 Adam 拒绝吃甜点，第 4/5 块里别人对话回忆起“你 6 岁时在蹦床上摔断了手”。切块抽出之后，汇总阶段没分清“人物口述回忆的时间”和“剧本出场顺序”，把顺序排错了（D!=B），而全量直读因为保留了完整语境反而是对的。
